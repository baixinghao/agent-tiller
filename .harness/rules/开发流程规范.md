# 开发流程规范

## 十阶段流水线

| Stage | Name | Quality Gate | Output |
|-------|------|-------------|--------|
| 1 | 需求分析 | 需求清晰无歧义，业务价值明确 | 需求文档 + 影响分析 |
| 2 | 方案设计 | 方案经过评审，技术选型有依据 | 技术方案 + 变更记录（涉及 rules/ 修改时需 EVOLUTION_LOG ADR） |
| 3 | 任务拆分 | 任务粒度 ≤ 4h，依赖关系明确 | 任务列表 + 执行顺序 |
| 4 | 编码实现 | 遵守编码规范，红线零违反 | 可编译代码 |
| 5 | 单元测试 | 覆盖率 ≥ 80%，核心逻辑 100% | 测试报告 |
| 6 | 代码评审 | 评审通过，无 🔴 问题 | 评审记录 |
| 7 | 集成测试 | 接口联调通过，数据流正确 | 集成测试报告 |
| 8 | 预发验证 | 预发环境验证通过 | 验证记录 |
| 9 | 上线部署 | 部署脚本执行成功 | 部署记录 |
| 10 | 线上观测 | 监控无异常，业务指标正常 | 观测报告 |

## 回滚路线表

| Stage | Rollback Strategy | Trigger |
|-------|-------------------|---------|
| 编码实现 | git checkout -- 丢弃变更 | 编译失败 |
| 单元测试 | 修复测试或回退代码 | 测试失败率 > 20% |
| 代码评审 | 修改评审意见 | 🔴 问题未解决 |
| 集成测试 | 回退到上一个稳定版本 | 接口不通 |
| 预发验证 | 回退到生产版本 | 功能异常 |
| 上线部署 | 回滚到上一版本镜像 | 冒烟失败 |

## 变更管理目录结构

```
.harness/changes/
├── active/              # 进行中的变更
└── shipped/             # 已上线的变更
    └── {feature-name}/
        ├── summary.md          # 变更概述
        ├── db-migrations.sql   # 数据库变更
        └── rollback.sql        # 回滚脚本
```

每个变更必须包含 `summary.md`，记录：
- 变更概述
- 影响模块
- 数据库变更
- API 变更
- Redis 变更
- 关键约束
- 回滚方案

## COLA DDD 标准工作流程

### A. 新增业务功能（在已有 DDD 模块内）

```
Step 1.  阅读 .harness/specs/{module}/  确认模块定位与边界
Step 2.  数据库    .harness/changes/active/{feature}/db-migrations.sql
Step 3.  Domain    新增领域模型（聚合根/实体/值对象）+ DomainException
Step 4.  Policy    新增领域规约（纯函数，domain/policy/validation/）
Step 5.  ACL       新增防腐层接口（domain/acl/）+ 实现（infrastructure/aclImpl/）
Step 6.  Repository 新增仓储接口（domain/repository/）+ 实现（infrastructure/persistence/）
Step 7.  AppService 新增应用服务（application/service/）+ Command（record）
Step 8.  Assembler  新增转换器（interfaces/assembler/）
Step 9.  Controller 新增控制器（interfaces/rest/）+ DTO
Step 10. DomainConfig 更新领域 Bean 装配
Step 11. 测试      参照 skills/unit-test-write/SKILL.md
Step 12. API_REGISTRY.md 登记 URN
```

### B. 修复 Bug

```
Step 1. 复现问题  确认是后端/数据/外部服务问题
Step 2. 定位根因  按数据流查找（Controller → AppService → DomainService/Policy → ACL/Repository → Infrastructure）
Step 3. 修改代码  最小改动原则，不引入无关变更
Step 4. 验证修复  确保 DomainException 正确抛出和处理
Step 5. 回归测试  确认改动不影响已有功能
Step 6. 更新文档  更新对应 .harness/changes/ 和 specs/
```

### C. DDD 重构（遗留模块迁移）

```
参照 skills/harness-api-refactor/SKILL.md 的 8 步工作流
```

## 质量门禁

| 门禁 | 检查项 | 说明 |
|------|--------|------|
| QG-1 | 模块放置正确 | 代码放在正确的模块和层，不跨越依赖边界 |
| QG-2 | 命名符合规范 | 类名/方法名/变量名遵循项目约定 |
| QG-3 | DDD 分层正确 | Controller→AppService→Domain→Infrastructure，依赖方向正确 |
| QG-4 | 领域层纯净 | domain/ 下无 Spring 注解，Policy 纯函数 |
| QG-5 | 异常处理 | 业务异常使用 DomainException，全局异常已统一处理 |
| QG-6 | ACL 隔离 | ACL 返回领域值对象，不泄露外部 DTO |
| QG-7 | 测试覆盖 | 核心业务逻辑至少覆盖正常路径和主要异常路径 |
| QG-8 | 无重复轮子 | 检查是否有现成的工具类/组件可复用 |
| QG-9 | 不影响现有功能 | 确保不引入回归问题 |
| QG-10 | 文档同步 | 变更记录写入 .harness/changes/，summary.md 必须含知识蒸馏章节（归档 shipped 前校验，见 rules/03_SELF_EVOLUTION.md §2） |
| QG-11 | harness_gate 通过 | pre-commit 门禁无 CRITICAL（python .harness/tools/harness_gate.py --fast） |
